- Keep navigation grouped through GroupedNavigation with secondary section views, so every feature remains accessible without overcrowding the header.
- Merge single-board and bulk-board updates into the same client leaderboard state, preserving observed PB improvements when older snapshots arrive, so profile totals stay synchronized.
- `/api/all-leaderboards` warms its persisted snapshot in `BATCH`-sized slices per request (`src/routes/api/all-leaderboards.ts`). Never fetch all `LEVELS` in one refresh: the upstream limit is ~120 req/min and a full deep load is 216 requests (~113s), which exceeds the handler's 20s wait, so nothing persists and `loaded` stays 0. Successive requests advance the warm-up and each completed slice is written to the `app_docs` snapshot.
- Profile medal data comes from the live `/user/{username}` fields `medal_counts`, `medal_counts_packs`, `medal_counts_community` (tiers: bronze/silver/gold/platinum/author), plus `custom_levels_completed`, `maps_completed`, `total_maps`, and `daily_stats`. The old `custom_medals`/`official_medals`/`pack_medals` fields never existed upstream — don't reintroduce them.
- Replay input decoding lives in `src/lib/replay.ts`: `inputs` is base64, 4 two-bit symbols per byte (MSB pair first), sampled at 240Hz (1000/240 ≈ 4.1667ms/tick). Symbols: 0=neutral/coast, 1=right steer, 2=left steer, 3=brake (both steer directions held). `ReplayViewer` collapses runs into held segments like `r72`.
- Replay physics (`src/lib/replay-sim.ts`) no longer approximates the game's `Player`. It drives the exact engine - the same Rust/WASM `GameMechanicsEngine` the Flutter app loads via `physics_core_capacitor.js` - bundled at `src/lib/physics/{rust.js,rust_bg.wasm}`. `simulateRun` is async and records one point per 240Hz input tick (`SIM_TICK_MS = 1000/240` in `replay-sim.ts`; `REPLAY_TICK_MS = 1000/240` in `replay.ts`), so the arrow's recorded rotation animates even on a spin that never translates. `SimPoint` carries the engine's own `rotation` (`rot = rotation - PI/2`) and the renderer draws the heading straight from it — never from sample displacement, which froze spins against walls. `ReplayEngine` exposes `step`/`reset`/`snapshot`/`restore` so a scrub can rewind instead of re-running from spawn. The engine's `rotation` is 0 facing -y. Symbol mapping: 1=right, 2=left, 3=brake.
- **Each arrow has its own physics.** The engine ships only a neutral default (`create_default_game_state()`), and that default is a mix of Narrow's power/startup with Speedy's energy/traction, so using it for every run makes replays DNF against walls the real run cleared. `simulateRun` now takes the run's `arrow_name` and overrides `player.constants` from `ARROW_CONSTANTS` in `replay-sim.ts` (Narrow/Speedy/Energy). Those ten values (`radius`, `engine_power`, `engine_startup_ticks`, `energy_capacity`, `energy_regeneration`, `traction_power`, `brake_power`, `aerodynamics`, `oiliness`, `turning_speed`) are the exact constants the client feeds the engine, recovered from the game's compiled Dart (`bui` in `main.dart.js`). With them, replays reproduce recorded completion times to within 1–2 ticks (verified for all three arrows on Highway Jet, and Energy on RitF).
- The bundled engine at `src/lib/physics/{rust.js,rust_bg.wasm}` supports the full `ApiObstacle` schema: `wall`, `zone` (boost/ice/nosteer/steer/rail, optional `zone_direction`), and `portal` (`portal_id` + `side`). `engineObstacles` passes every field the level uses through verbatim (`wall_type`, `wall_thickness`, `zone_type`, `zone_direction`, `portal_id`, `side`, `rotation_pivot`, `rotation_speed`, `speed`) and only infers `obstacle_type` when the payload omits it. The engine is extracted from the current Android APK (`assets/flutter_assets/assets/wasm/`) — the retired web build (`play.narrowarrow.xyz`) predates rails and portals, and the archived wasm (2026-06-13) ignores `rail` zones entirely, so don't downgrade the wasm. Rails guide the arrow along the zone's axis; without them rail levels DNF.
- Custom-level leaderboards (`CustomsView.tsx`) render the same `ReplayViewer` per row as the main leaderboard, so replays work after searching/selecting a custom level too.
- Spinning obstacles (e.g. Arrow Factory, Spinner Pack) rotate about `rotation_pivot` by `rotation_speed * tick` (radians, 240Hz tick) — verified exact against the engine's `state`. `levelWalls` carries `pivot`/`rotationSpeed` on each `SimWall`, and `ReplayViewer` applies the same transform at the current tick and bounds the camera by the swept circle. The engine already simulates the rotation, so physics never needed fixing here — only the render.
- Replay obstacle colours live in `src/lib/replay-visuals.ts` (`wallVisual(type)` → `VISUALS`, unknown types hash to a hue; `ReplayViewer`'s `ReplayLegend` reuses it). Match the game's own level renders: normal walls white, death red, bouncy green, boost blue. Keep the type keys in sync with the engine vocabulary (`wall_type`/`zone_type`).
- The TAS editor (`src/components/TasEditorView.tsx`, "Tools" → "TAS editor") loads a run's inputs or a bare level, then shows the run as a run-length list of held inputs — `Start 0.000`, one row per hold (`n 80`, `l 37`, …) with `-`/`+` to shrink/grow that hold by one 240Hz tick, then `Finish`. Growing inserts a copy of the symbol after the hold (splice) and shrinking removes the last tick; both splice/merge adjacent segments, so the displayed lengths are always exact run-lengths of `symbols`. Every edit re-simulates with the real engine from the latest checkpoint at or before the changed index (`CHECKPOINT` inputs apart), so a change near the end of a long run only re-steps the tail. It reuses the shared `ReplayStage` (exported from `ReplayViewer`) with `hideControls`. The "Leaderboard" popover lists the selected level's board so a run can be picked by name (auto-switches level/arrow). "Go to time (s)" jumps the frame; note `path[0]` is the spawn pose so input `i` lands on `path[i + 1]`.
- The leaderboard cache (`src/services/api.ts`) merges via `mergeLeaderboardUpdates` (`src/lib/leaderboard-state.ts`) on both the bulk and single-board paths, so a single-board refresh never drops a PB the bulk snapshot already surfaced. The `all-leaderboards` route warms the persisted `app_docs` snapshot in `BATCH`-sized slices per request; never fetch all `LEVELS` in one refresh (upstream limit ~120 req/min; a full deep load exceeds the handler's 20s wait).
- The upstream API (`api.narrowarrow.xyz`) is read-only in this repo: every route is a `GET` through `na-proxy.ts`, and the run payload (`/runs/<id>`) is `{ runId, mapName, arrow_name, inputs, input_count, verified, completion_time, finishedAt, skinConfig, isCustomLevel }` — it carries no user id and no submit/upload endpoint. So a TAS run can't be pushed into the game's own leaderboard (nor onto a copied level) from here; the TAS board below is the sanctioned place to post one. Re-submitting to the real game would need a game account and the game's own client flow, which this site doesn't implement.
- The community TAS leaderboard is site-owned, not the real game board — it exists precisely so tool-assisted runs can be shared without touching the official leaderboard. Storage is `src/lib/tas-board.server.ts` (one `app_docs` doc per level, collection `tas_boards`, entries sorted by time then creation). The API is `src/routes/api/tas-leaderboard.$level.ts`: `GET` returns the level's sorted entries (anon-readable), `POST` validates the name/time/input string, appends, and returns `{ isRecord, rank, entries }`; `DELETE ?id=` removes one entry and is admin-only (`verifyAdminRequest` re-checks `user_roles` server-side, so hiding the button in the UI is not the gate). Client helpers live in `src/lib/tas-leaderboard.ts`. The editor's "Submit TAS" button opens `TasSubmitDialog` (name + fixed time; the input string is attached automatically from the current `symbols`), and the editor shows the level's TAS board with a "New TAS record!" toast when the submitted time beats the existing best. `app_docs` writes need the service role, which local dev lacks — `tas-board.server.ts` falls back to a per-process in-memory board when `SUPABASE_SERVICE_ROLE_KEY` is unset and `NODE_ENV !== "production"`; production always uses Supabase.
- The TAS board (`TasLeaderboardView`, "Tools" → "TAS leaderboard") lists the selected level's entries with the fastest pinned as `WR`. Every row can be watched in-place via `TasReplayViewer` (`ReplayViewer.tsx`), which plays straight from the stored input string with the real engine — no upstream run id needed — and loaded into the editor via the pencil button, which hands a `TasLoadRequest` (`{levelId, arrowName, inputs, inputCount}`) up through `App` to `TasEditorView`. Submissions must be distinct runs: `POST` rejects an input string already on the board with `409`, so a loaded WR can't be re-submitted untouched (edit it first). Its wide table (7 columns) must stay inside an `overflow-x-auto` wrapper — without it the rightmost Actions column (watch/load/delete) is clipped off-screen and unreachable on narrow viewports, since the enclosing card is `overflow-hidden`.
- The main leaderboard shows the level's community TAS time instead of the old theoretical/human limit cards. It is fetched per selected level via `fetchBestTasTime` and renders `N/A` when the level has no TAS submissions.
- The TAS replay viewer can compare runs: `TasReplayViewer` takes the rest of the level's board as `boardEntries` (wired in from both `TasLeaderboardView` rows and the editor's mini-board) and lists them as tickable ghosts. Each ticked run is re-simulated with its own `arrowName` against the one cached level geometry (`levelData`) — never a second geometry fetch — and handed to `ReplayStage` as `overlays`. Ghosts draw first (tinted trail, alpha 0.6 arrow, name·time label) so the primary run's trail and arrow stay on top; the camera bounds union the ghost paths and the scrubber extends to the longest run. Colours cycle `GHOST_PALETTE` in `src/lib/compare-ghosts.ts` by board order, so a ghost keeps its colour as others are toggled.
- The TAS "Brute optimizer" (`BruteView.tsx`, Tools group) is admin-gated: it seeds a search from the selected level's fastest TAS run and hill-climbs the input string with the real engine (`optimizeRun` in `src/lib/tas-brute.ts`), then offers "Submit as my TAS" through the same `TasSubmitDialog`. Non-admins get a "still in development" notice. Because the run must be a *new* line to submit, the optimizer output has to differ from the seed input string (`POST` rejects exact duplicates with `409`).
- When optimizing a replay offline, always feed the engine the run real `arrow_name` constants (`ARROW_CONSTANTS` in `replay-sim.ts`) - with the default constants a valid run DNFs, and any time measured against it is meaningless. Reusing the engine `GameMechanicsEngine.from_state` snapshot at a checkpoint is ~2x faster than re-running the prefix, so an incremental search over the tail is the practical way to squeeze a run.
- Input semantics (from instrumenting the engine on open ground): symbol 0 (neutral) coasts along the current heading and thrusts straight ahead, accelerating to a terminal ~2.39 for Narrow; a held turn (1 right / 2 left) rotates the heading ~0.013 rad/tick, so the thrust points away from the velocity and bleeds speed (circling settles at ~0.52). So a straighter line is faster and the level's walls do the turning for you; a real maze run reaches ~1.6 because corners force turning. Symbol 3 (brake) scrubs speed hard. The trajectory is slidey (`oiliness` 0.996), so the arrow drifts and the heading often sits well off the velocity.
- The offline hill-climb plateaus after a few ticks, so the productive search is simulated annealing plus a "straighten" mutation that replaces held turns in a random window with neutral (exploiting the speed-vs-turn trade-off above). For Moon Rock Rally (`0CFAEE35`) this took the Narrow line 11.829s (real WR) -> 11.7458s in ~1h on 4 cores; ~1 tick per 10 min once near the plateau.
- Discord record tracking has two feeds sharing one webhook config doc (`configs/discordTracker`): the real-game category notifier (`src/routes/api/public/category-wr-check.ts`) and the TAS notifier (`src/routes/api/public/tas-wr-check.ts`). Both are admin-configured in `AdminDiscordTracker.tsx` (Discord tab) with per-arrow emoji/templates, and both post to the same webhook unless the TAS feed sets `tasWebhookUrl`. The TAS feed announces only the fastest TAS run per level+arrow (`[WR -x.xxx]` = how far ahead of the real WR, `[TAS -x.xxx]` = gain over the previous TAS), reading the board from `tas-board.server.ts` and fetching the real WR from the upstream API only for levels that already have a TAS board. Each feed keeps its own baseline (`configs/categoryRecordState` / `configs/tasRecordState`); first run is a silent baseline, and the `intervalMinutes` gate is per feed.
- The TAS editor's Import accepts more than its own export. `parseTasFile` (`src/lib/replay.ts`) normalises any of the TAS file shapes in the wild to the raw symbol stream: `{inputs}` (base64, the editor's export), `{syms}`/`{symbols}` (the offline optimiser's output, often saved as `*.json.txt`), a bare `[0,1,2,3,…]` array, or a run-length `{segments:[{key|short,length}]}` list. It also reads `arrow_name`/`arrow` and `map_name`/`level_id`, so an imported file can open its own level and arrow; `f`/`finish_tick` is shown in the status line. The file input's `accept` includes `.txt` and `text/plain` because a `.json.txt` is a `text/plain` file and would otherwise be greyed out in the picker.
- The shallow `/api/leaderboard/<id>` board is a **global top-150** cut, so it hides the real best time for a *specific arrow* (e.g. Turnpike Drift's true energy best 16.683s was missing while narrow 16.392s dominated the 150). Always read `?deep=1` (per-arrow merge, see `fetchLevelBoard` in `src/lib/leaderboard-source.ts`) when you need a per-arrow seed. Note the site's own board can also lag upstream: new runs (e.g. an 18.058s energy PB) can sit on a stale snapshot until the bulk refresh cycles.
- Main-board render is kept snappy by four App.tsx choices: search filters through `useDeferredValue(searchQuery)` so typing never blocks on the board re-sort; the board's fastest time is memoised once as `boardWrTime` (the old per-row `Math.min(...processedData.map(...))` made the table O(n²)); leaderboard rows animate with a fixed `transition={{ duration: 0.15 }}` and **no per-row stagger** (the old `delay: Math.min(index*0.03, 0.5)` cascaded for up to half a second on every filter change); and the arrow-column filter uses `Set` + `useMemo`, never a per-row `.filter()`. Keep new per-row work out of the `.map()` body.
- The offline brute harness (`/workspace/taswork/opt.ts`) `perturb` must recompute its editable-index pool after every splice — a pool captured once up front indexes past the array once a splice shrinks the segment list and crashes with `Cannot read properties of undefined`. Level data comes from `api.narrowarrow.xyz/level-details/<id>?isCustomLevel=true`; real runs from `api.narrowarrow.xyz/runs/<id>` (`{runId,mapName,arrow_name,inputs,input_count,verified,completion_time,...}`); the DNF fitness gradient derives its goal from the level's own `finish` wall midpoint, not a hardcoded point.
- The brute harness's DNF fitness gradient can be a trap when the level's `finish` wall sits **behind a death wall** (Turnpike Drift: finish #33 and death #26 are parallel, so the finish *midpoint* is unreachable and the gradient parks a run against the death wall). Aim the gradient at the reachable entry instead — `FTARGET=x,y` in `opt.ts` (e.g. the finish wall's lower corner) — and add `MINDEPTH=y` so a run cannot shorten its DNF by turning back before the slalom. When a search plateaus a few units from the goal, always check the death tick against the edit window (`WIN`) — a window that stops before the death can never touch the fatal ticks.
- `BAN_BRAKE=lo,hi` forbids the brake symbol in a tick range, so the search must make that turn some other way. Useful for testing "can this corner be taken without braking" — but on a tight weave the brake is often load-bearing: the arrow (~22 units wide) threads a channel barely wider than itself, so removing the brake DNFs. A run that clears the weave brakeless is not automatically faster either; on Turnpike Drift a brakeless line reached the finish *area* ~5s early yet could not enter, because the finish is only reachable from the opposite side of the death wall.
- Turnpike Drift (`ADEEF62A`) is a "spinner pack" level: obstacles `#0-19` rotate about the shared pivot `(-510,-30)` at ±0.001 rad/tick, and they are drawn as **car shapes** (a chassis with two wheel-like bars). Only `#0-19` rotate — `#20-53` (including the finish `#33` and death `#26` walls) are static, so `rotation_pivot: null, rotation_speed: 0` in the level payload means the wall does not move. The fast lines **bank off the moving car** to enter the finish: the speedy 16.550s run hits car `#5` at `(-745,-137)` on t3730 and its velocity flips from `(-1.44,+1.67)` to `(+0.51,+1.06)`, redirecting it up-right into the finish (the bounce costs ~1.0 speed). When checking wall contacts, compare against `arrow_radius + wall_thickness` (thickness 8, so contact ≈ radius + 4), not the radius alone — otherwise real bounces read as "no contact".
- The upstream leaderboard endpoint is `api.narrowarrow.xyz/leaderboard?levelId=<id>` (a bare `/leaderboard/<id>` 404s with "Level not found"). Arrow Vortex is `5B719122` (spinner-pack); the Energy WR there was 12.713s and the offline harness (seeded from that run) reached **12.508s**, a −0.205s improvement, uploaded to the site's TAS board. Speedy is by far the slowest arrow on the spinner levels (its long startup/warm-up), so optimise Energy/Narrow there, not Speedy.
- Soft WRs are the cheapest wins: seed the harness from the upstream best run for an arrow, and if it drops the time the level's board is soft. Sessions found and uploaded (all rank-1 `isRecord` unless noted): Apex Rush `6D4FA12C` Energy 25.308→**23.204** (softest, −2.10s); Level Drift `1776364690787` Energy 18.308→**17.971**; Colossal R `AAA35C8F` Narrow 13.658→**13.575**; Maze Rally 2.0 `1777481332692` Narrow 15.383→**15.238**; Final Drift `723F4248` Narrow 11.925→**11.821**; Arrow Vortex Energy 12.713→**12.508**; Fast Spinners `7913D7AD` Narrow 13.683→**13.637** (rank 2) and Speedy 14.5→**14.463** (rank 3); Level 1 `6D8E28FA` Speedy 12.3→**12.283**. Energy WRs on the spinner/precision levels tend to be the softest, so try Energy first. A hunt that keeps re-finding the exact WR time is a genuine local optimum (Turnpike Speedy 16.550, Windmill Land 11.642/13.075, Spinning Square 14.079, Arrow Factory 16.696) — leave it and move to another level/arrow rather than burning cores.
- The site's brute optimizer matches the reference tool (`replay-tools.sirsamyoudev.workers.dev`) operator-for-operator (8 RLE moves, reheat at T<0.15, then 1-tick coordinate-descent refine) and beats it on speed: this site's per-tick `GameMechanicsEngine` + `stepCode` (`replay-sim.ts`) is ~4.3ms/run vs the reference's batched `MultiPlayerEngine` `simulateTicks` at ~15.6ms/run (a 3.6x advantage). A controlled A/B on Moon Rock Rally (`0CFAEE35`, seed 11.746s) showed both stacks plateau on the optimum, and on a degraded DNF seed only the combos using this engine recovered the finish. Never "fix" the optimizer by swapping in the reference's engine path; the reference's only real edge was running off-thread, now fixed by the worker.
- `optimizeRunLite` (`tas-brute.ts`) returns the winning stream + score with no trajectory; `optimizeRun` is a thin wrapper that adds the `simulateRun` trajectory. `BruteView` runs `workerCount()` (cores-1, capped 8) workers in parallel, each with its own `rngSeed`, and keeps the best - independent restarts escape the annealer's plateau better than one long run. Simulate the winner's trajectory once on the main thread after all workers finish, never per worker. The worker messages carry `BruteResultLite`; `BruteView` imports `BruteResult` only for the preview.
