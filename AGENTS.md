- Replay input decoding lives in `src/lib/replay.ts`: `inputs` is base64, 4 two-bit symbols per byte (MSB pair first), sampled at 240Hz (1000/240 Ōēł 4.1667ms/tick). Symbols: 0=neutral/coast, 1=right steer, 2=left steer, 3=brake (both steer directions held). `ReplayViewer` collapses runs into held segments like `r72`.
- Replay physics (`src/lib/replay-sim.ts`) no longer approximates the game's `Player`. It drives the exact engine - the same Rust/WASM `GameMechanicsEngine` the Flutter app loads via `physics_core_capacitor.js` - bundled at `src/lib/physics/{rust.js,rust_bg.wasm}`. `simulateRun` is async and records one point per 240Hz input tick (`SIM_TICK_MS = 1000/240` in `replay-sim.ts`; `REPLAY_TICK_MS = 1000/240` in `replay.ts`), so the arrow's recorded rotation animates even on a spin that never translates. `SimPoint` carries the engine's own `rotation` (`rot = rotation - PI/2`) and the renderer draws the heading straight from it ŌĆö never from sample displacement, which froze spins against walls. `ReplayEngine` exposes `step`/`reset`/`snapshot`/`restore` so a scrub can rewind instead of re-running from spawn. The engine's `rotation` is 0 facing -y. Symbol mapping: 1=right, 2=left, 3=brake.
- **Each arrow has its own physics.** The engine ships only a neutral default (`create_default_game_state()`), and that default is a mix of Narrow's power/startup with Speedy's energy/traction, so using it for every run makes replays DNF against walls the real run cleared. `simulateRun` now takes the run's `arrow_name` and overrides `player.constants` from `ARROW_CONSTANTS` in `replay-sim.ts` (Narrow/Speedy/Energy). Those ten values (`radius`, `engine_power`, `engine_startup_ticks`, `energy_capacity`, `energy_regeneration`, `traction_power`, `brake_power`, `aerodynamics`, `oiliness`, `turning_speed`) are the exact constants the client feeds the engine, recovered from the game's compiled Dart (`bui` in `main.dart.js`). With them, replays reproduce recorded completion times to within 1ŌĆō2 ticks (verified for all three arrows on Highway Jet, and Energy on RitF).
- The bundled engine at `src/lib/physics/{rust.js,rust_bg.wasm}` supports the full `ApiObstacle` schema: `wall`, `zone` (boost/ice/nosteer/steer/rail, optional `zone_direction`), and `portal` (`portal_id` + `side`). `engineObstacles` passes every field the level uses through verbatim (`wall_type`, `wall_thickness`, `zone_type`, `zone_direction`, `portal_id`, `side`, `rotation_pivot`, `rotation_speed`, `speed`) and only infers `obstacle_type` when the payload omits it. - When optimizing a replay offline, always feed the engine the run real `arrow_name` constants (`ARROW_CONSTANTS` in `replay-sim.ts`) - with the default constants a valid run DNFs, and any time measured against it is meaningless. Reusing the engine `GameMechanicsEngine.from_state` snapshot at a checkpoint is ~2x faster than re-running the prefix, so an incremental search over the tail is the practical way to squeeze a run.
- Input semantics (from instrumenting the engine on open ground): symbol 0 (neutral) coasts along the current heading and thrusts straight ahead, accelerating to a terminal ~2.39 for Narrow; a held turn (1 right / 2 left) rotates the heading ~0.013 rad/tick, so the thrust points away from the velocity and bleeds speed (circling settles at ~0.52). So a straighter line is faster and the level's walls do the turning for you; a real maze run reaches ~1.6 because corners force turning. Symbol 3 (brake) scrubs speed hard. The trajectory is slidey (`oiliness` 0.996), so the arrow drifts and the heading often sits well off the velocity.
- The offline hill-climb plateaus after a few ticks, so the productive search is simulated annealing plus a "straighten" mutation that replaces held turns in a random window with neutral (exploiting the speed-vs-turn trade-off above). For Moon Rock Rally (`0CFAEE35`) this took the Narrow line 11.829s (real WR) -> 11.7458s in ~1h on 4 cores; ~1 tick per 10 min once near the plateau.

- The brute optimizer (`tas-brute.ts`) scores every candidate through `CheckpointSim`, which skips the shared prefix instead of re-running from spawn: it snapshots a reference stream every 60 ticks (`stride`), finds the deepest checkpoint whose whole prefix matches the candidate, restores it and steps only the tail. Candidates that edit early miss and fall back to a full replay. The search re-anchors the checkpoints via the `onRef` hook (called on every accepted anneal move and every refine improvement); `setRef` rebuilds only the tail past the divergence, so following `cur` is cheap. - **Video export encodes offline with WebCodecs, not `MediaRecorder`.** `MediaRecorder` captures the canvas in *real time*, so under load it drops/janks frames and — the reported bug — freezes the tail of the run because the encoder is still catching up when `stop()` fires (a 13.8s run took ~13.9s of wall clock, and the last ~1s could be missing). `exportReplayVideo` now prefers `tryExportOffline`: it renders every frame at its exact timestamp, feeds them to a `VideoEncoder`, and muxes the chunks. Result: frame-exact duration (verified 13825.000ms for a 13.825s run at both 640×360 and 1280×720), every frame present, and ~2–6× faster than real time depending on resolution. `exportWithMediaRecorder` is kept only as a fallback for browsers without WebCodecs; `canExportOffline()` gates the dialog's supported message and its description text.
- **The exporter writes MP4/H.264, not WebM/VP9.** WebM is not a universal container: QuickTime, Windows Media Player, many mobile galleries and older Safari cannot open it at all and show their media-error placeholder (a grey frame with a sad face) — the reported bug. The default output is now H.264 in MP4 via `src/lib/mp4-muxer.ts` (a minimal ISO-BMFF writer: `ftyp`, `moov` with one `trak` carrying `avcC`/`stts`/`stss`/`stsc`/`stsz`/`stco`, then `mdat`; all samples in one chunk so `stco` is a single offset). `pickEncoderCodec` tries `avc1` first and only falls back to VP9/VP8 (`src/lib/webm-muxer.ts`) if the browser cannot encode H.264; `avcCodecs(pixels)` picks a level that actually covers the frame size (`avc1.420028` ≤720p, `avc1.42002A` ≤1080p, `avc1.420033` larger — level 3.1 silently fails `isConfigSupported` above 720p, which is why 1080p used to fall back to WebM). The H.264 `avcC` is the encoder's own `decoderConfig.description` (captured from the first chunk's metadata), and the filename extension follows `blob.type`.
- **Both muxers stream; they do not buffer the clip.** `Mp4Writer` and `WebMWriter` (`mp4-muxer.ts`/`webm-muxer.ts`) are append-only: `tryExportOffline`'s `VideoEncoder` `output` callback hands each encoded chunk straight to `addFrame`, and `finish()` appends only the small header tables (MP4 `moov`; WebM's last cluster). Previously every frame was collected in an array and the whole file built in one pass at the end, so the clip existed twice in memory at the finish (encoded frames + the concatenated `mdat`) and a long/high-resolution export peaked high enough to crash the tab — the reported bug. The MP4 writer measures the header once (a zero `stco` offset) to learn the `mdat` offset, then rebuilds it (the size is fixed, so the measure is exact), and passes the header boxes and the frame `Blob` parts to `new Blob([...])` so each byte is copied once. **Each frame is stored as its own `Blob`** (`addFrame` does `new Blob([data])`, WebM likewise per cluster), not as a retained `Uint8Array`: the bytes then live outside the JS heap and `finish()`'s `new Blob([...])` composes them by reference, so the export's marginal heap stays ~30-40MB instead of the whole clip. The WebM writer wraps each keyframe-delimited group of blocks in a `Cluster` element (writing them straight into the `Segment` is unreadable by any demuxer). Verified by driving the real `exportReplayVideo` in headless Chromium (CDP) across every geometry/theme/mode combination and decoding each output with `ffmpeg -f null -` (no errors), including a real Highway Jet WR run at 1080p (frame-exact 13.825s).
- **Export tuning is memory-aware, because the crash is a renderer OOM ("Aw, Snap"), not a container bug.** The symptom is Chrome killing the tab near the end of a long/high-resolution export (and on phones at low resolution), worse the longer the run: `planEncode` (`replay-export.ts`) picks a bitrate (default ≈12% of raw) and, only if that still overflows `EXPORT_CLIP_BUDGET_BYTES` (32MB) for the run's duration, a lower one down to a floor, then drops the frame rate (min 15fps) for very long runs. Effect: a 519s run went from a 9.7MB/208s clip to 3.9MB/70s, and the peak heap from ~180-284MB to ~150-200MB, with the encode itself no longer scaling with length. The realtime `MediaRecorder` fallback (`exportReplayVideoRealtime`, only reached when WebCodecs is absent) uses the same `planEncode`, since it buffers the whole recording too.

- **Never read the engine's pose per tick unless a mechanic needs it.** `read()` is `JSON.parse(engine.state)` — a parse of the *whole map*, so it costs ~0.0094ms per obstacle (measured): ~3ms on the endless course's ~1600 walls, but 0.0001ms for the scalar `player_state_code()`. `stepCode`/`step` read the pose before each step only to feed `applyTriggers`/`armWire`, which are the sole consumers of the *previous* pose; endless has no switch/breakable/wire, so the read was ~99% of the frame and made the mode go slow *and get slower* as the course grew. - **Play's `path` is frame-sampled, so never derive a tick from `path.length - 1`.** The engine steps a fixed 240Hz but `PlayGame.advance` appends one path point per *rendered frame* (several ticks per frame on a normal display), so `path.length - 1` is the frame count, not the tick. `PlayGame` exposes the true tick (`currentTick`) and stamps each point with its tick (`pathTicks`, parallel to `path`); `PlayCanvas` must use those for anything per-tick — wall rotation, moving-block offsets, the thrust flicker, marker dots (resolve a marker tick to its stamped point, do not index `path` by tick). Deriving the angle from `path.length - 1` drew a spinning obstacle ~4× behind its own hitbox (measured 123° at 30fps), which read as the arrow flying inside the spinner. `rewindTo` trims frame samples by tick stamp, not by index. `simulateRun` (replays/TAS) records one point per tick, so replays are unaffected — only Play. `scripts/verify-play-tick.ts` drives the real loop at a throttled frame rate and asserts the drawn angle matches the engine (0.0000 rad).
- **Moving/sliding blocks are a site-only obstacle the sim animates, because the engine can only *rotate* an obstacle, not translate one.** The engine reads obstacle geometry from state and mutates it per tick (that is how `rotation_speed` bakes in), so a moving block is done the same way the wind/suction force fields are: `createReplayEngine`'s driver (`src/lib/replay-sim.ts`) rebuilds the engine from state after each step with the block's points offset. Fields: `motion_dx`/`motion_dy`/`motion_period` on the `RawLevelData` obstacle (site-only, stripped from the game export just like fields). `motionOffsetAt(dx, dy, period, tick)` is a there-and-back triangle wave — offset reaches `(dx,dy)` at `period/2` ticks and returns to zero at `period` — so the block is momentarily still at each end. `isMovingBlock` rejects a zero offset/period so a static wall never triggers a rebuild; `levelMotions` lists every mover with its `data.obstacles` index, and `createReplayEngine` maps that to the *engine* obstacle index (`engineIndexOf`, fields excluded) to know which points to rewrite. **`SimWall.motion` indexes `SimGeometry.movingBlocks` (the dense mover list), not `data.obstacles`** — `levelGeometry` builds that map up front; the renderer (`paintWalls` via `PaintCtx.motions`, `ReplayViewer`'s camera `reach`, the editor canvas travel line) relies on it. Snapshots are returned as-is: `applyMotions` sets points *absolutely* (base + offset), so restoring a mid-run state never double-applies the motion — do not "clean" the points back to base on snapshot, that reintroduces a one-tick error. `nalvl` round-trips the three fields (editor "Moving" toggle with offset + period); the site-level publish whitelist in `src/routes/api/site-levels.ts` must keep them (and `rotation_*`, which it used to drop). `scripts/verify-moving-blocks.ts` proves the translation changes the real sim, snapshot/restore is consistent, and the render-index mapping holds with statics interleaved.


- **Endless mode (Play → Endless) is a generated course scored by sections passed, not time.** The engine takes a level's whole obstacle list up front and has no score channel, so "endless" is one long deterministic course built from a seed (`src/lib/endless.ts`, `buildEndlessCourse`) — seed + input string reproduces a run exactly. The course runs along -y with a meandering centreline; every piece is a series of *gates* (a horizontal wall with a gap on the centreline). Gates are deliberately horizontal, never full-height vertical walls: a vertical wall would trap the arrow on the wrong side forever, whereas a gate always leaves a reachable gap ahead. Gates are lethal (`death`), so "try not to die" works natively — the engine latches `dead` at the contact tick — and a run always ends decisively instead of stalling on a normal wall. Score is one point per boundary crossed (`sectionsCrossed`/`SectionMarker`), counted forward as the arrow passes; each marker carries the `piece` label of the section that ends there, for split-style UI. The corridor (`COURSE_WIDTH` 640, `DEFAULT_GAP` 190 → `MIN_GAP` 155) and meander (`MAX_MEANDER` 190) are sized to the arrow's real control model — it turns only ~1 rad per 2 s of held steer and curves rather than sliding, so a wide meander looks dramatic but cannot be followed. A *corner* is a piece whose centreline jumps sideways by a large step; the jump is capped at `MAX_CORNER` (250) because the arrow only travels about half as far sideways as forward per piece, so a bigger corner's gap would be unreachable. `EndlessView.tsx` reuses `PlayGame` (fixed-240Hz real engine) and `PlayCanvas` (follow camera) so it plays exactly like the Play tab; mobile taps the left/right half of the stage, and a tap while idle starts the run.
- **Endless scores are a site-owned board, and there is one global board — not one per seed.** The score is sections survived, which measures the player, not the course, so every seed feeds the same list; a run still records the seed it was set on (shown in the table) so a course can be reproduced. Storage `src/lib/endless-board.server.ts` (one `app_docs` doc, collection `endless_boards`, entries sorted by score descending then creation), API `src/routes/api/endless-leaderboard.ts` (`GET` anon-readable, `POST` validates name/score/inputs and appends, `DELETE ?id=` admin-only via `verifyAdminRequest`), client `src/lib/endless-leaderboard.ts`. Like the TAS board it has no server-side verification — the engine does not run server-side in this repo — so it trusts the client score but rejects a duplicate input string (`409`), and the stored inputs are the record of the run. `EndlessView` submits the run's recorded symbols (from `PlayGame`, base64 via `encodeInputSymbols`) on death, and shows the global board below the stage.
- **An endless course is ~1400 walls, so every painter must cull to the visible rect.** `paintWalls`/`paintZones` in `src/lib/replay-paint.ts` take a `view` (`PaintCtx`) and skip anything off screen (`offscreen` + `wallBounds`, which accounts for rotation and moving blocks); `PlayCanvas.tsx` computes the padded world rect from the camera each frame and passes it in. Without it a frame issues ~6500 canvas ops (~0.46 ms just to record, far worse on a phone GPU) against ~24 culled; this was the "so laggy" report on Endless. Never remove the `view` argument — the same painters draw short replay levels where the full draw is fine, but Endless needs the cull.

- **Accelerator wires thrust along the arrow's facing, never its momentum.** A wire is a site-only trigger (`accelerator_speed`/`accelerator_accel`, `isAcceleratorTrigger`) stripped from a game export; `armWire`/`applyWire` in `src/lib/replay-sim.ts` arm it on a segment crossing and thrust one tick at a time. Both the wire's normal orientation and the boost gate use the arrow's *heading* (`rotation - PI/2`), not `player.velocity`: after a turn, brake or bounce the momentum and the nose point different ways, and orienting by momentum made the boost fire against the nose (a backwards shove). Gate is `ACCELERATOR_MIN_ALIGN` (0.25, ~76 degrees); any non-coast input (`symbol !== 0`) starves the charge, and the push fades to zero at `targetSpeed`. Straight-coast runs are unchanged by the heading fix; only turn/brake crossings differ. The wire is drawn `#22d3ee` in both render modes (`ReplayStage`'s game branch calls `paintTriggersLocal`, `PlayCanvas` calls `paintTriggers`).

- **The four stateful site-only puzzle mechanics live in `src/lib/nalvl.ts` + `src/lib/replay-sim.ts`.** Kinds `switch`/`door`/`gate`/`blink`/`breakable` (`NALVL_PUZZLE_KINDS`, `isPuzzleKind`) are all site-only (`NALVL_SITE_ONLY_KINDS`), so `nalvlToGameData` strips them and `nalvlToRawLevelData` re-attaches them for the sim; the publish whitelist (`src/routes/api/site-levels.ts`) and `SiteLevelObstacle` must keep their fields (`switch_group`/`switch_action`/`door_start_open`/`gate_normal`/`blink_period`/`blink_duty`/`blink_phase`/`breakable`) or publishing silently downgrades them to plain walls. A switch is a sensor polygon the engine must never collide with, so `isNonEngineObstacle` excludes it; a door/gate/blink/breakable is a real wall in some state, so it reaches the engine and the sim *collapses it to a point off-map* (`collapsed`/`OFF_MAP`) when passable. A switch is one-shot per *group* (`firedSwitches`); door/blink/gate solidity is pure (`doorOpenAt`/`blinkSolidAt`/`gateSolidAt`) so the sim, `paintSiteMechanics` and the offline export all agree without extra state, while a door's open flag and a broken wall travel in the snapshot envelope (`SiteTimeline`). `gate_normal` points from the *blocked* side toward the passable side, so the editor's default gate normal is the draw direction rotated 90° CCW (a left-to-right horizontal draw yields `(0,1)`).
- **`paintSiteMechanics` must never be baked into `ReplayStage`'s static layer.** A door/blink/breakable changes with the tick, so a spawn-state bake would stay visible under the live per-frame pass; `paintWalls` skips any wall with `siteKind` and the live pass (`ReplayViewer.tsx`, `PlayCanvas.tsx`, `replay-export.ts`) draws them at the current tick with the run's `timeline`.

- **The site has a third Discord feed for site-hosted level records, alongside the real-game category feed and the TAS feed.** `src/lib/site-tracker.server.ts` mirrors `tas-tracker.server.ts`: config + baseline live in `configs/discordTracker` / `configs/siteRecordState`, `runSiteCheck(levelIds, {force, announceAll})` scans each level's single board (site levels have one board, not one per arrow), and the pure `decideSiteRecord(prior, bestMs, {isFirstRun, announceAll})` says whether a run is a record and whether to announce it. The announce rule distinguishes a *live submission* from a *bulk poll*: only a cold poll seeds a baseline quietly (so enabling the feed does not dump every pre-existing level's record at once), while a live submit always announces a new record — including a freshly published level's **first** record, which was silently baselined before and is the case that dropped a real WR (the submit path passes `fromSubmit: true`; `decideSiteRecord` must never treat a submission as seeding). It is driven from the same two places as the TAS feed: `GET /api/public/site-wr-check` (admin "Check site now" / `?announce=all`, plus any external cron) and the score submit handler in `src/routes/api/site-leaderboard.$level.ts`, which calls `runSiteCheck([level], {force:true})` on a new record so it is announced immediately (best effort). The shared `postDiscordMessage`/`isDiscordWebhook` helpers always send `allowed_mentions:{parse:[]}`. In local dev (no `SUPABASE_SERVICE_ROLE_KEY`) the tracker keeps config/state in process memory like the site level/score stores, so it is exercisable without Supabase; the admin UI is the "Site Level Webhook" / "Site Message" cards in `AdminDiscordTracker.tsx`. `scripts/verify-site-tracker.ts` covers the decision rule, template rendering (`{siteTag}`/`{clock}`/`{custom}`), the tidy-tags healing, a real `runSiteCheck` end-to-end over the in-memory stores, and delivery against a real local HTTP server. **The site feed has two editable messages** — a world record (a run that takes 1st) and a position (a run that places 2nd or worse) — with separate templates (`siteWrTemplate`/`sitePositionTemplate`) and a `{champion}` mark, all editable in the admin "Site Message" card. The WR template's bracket is `WR -x.xxx` (the gain over the previous record) and the position template's is `WR +x.xxx` (the gap behind the record); `{diff}` is the raw *signed* gap, so `tidySiteTags` resolves a literal sign in front of it in favour of the value's own sign (`[WR +{diff}]` with `-3.000` renders `[WR -3.000]`, not `[WR +3.000]`) — dropping the literal sign is what keeps a genuine negative gain from flipping. A config saved before the split holds the old default verbatim, which `resolveSiteTemplate` treats as "never customized" so the new wording applies, while a hand-written template is always kept. **A position is only visible to the submit path**, so `runSiteCheck` takes an optional `submission` (`SiteSubmission`: the run the route just stored, by id) and, when the level's best is *not* that submission, announces the submission's own placement instead. That guard matters: without it a slower submission on a cold tracker would announce the *existing* record holder's run (a cross-player announce) and skip the submitter's placement entirely. The poll path (no `submission`) still announces a level's new best as before, so the two never double-post.
- **The Play tab's 3-2-1 countdown lasts one second in total, and a restart returns the arrow to the start before it runs.** `COUNTDOWN_MS` (1000) is the whole countdown, split evenly across `COUNTDOWN_STEPS` (3) digits by `countdownDigit`, so each digit shows for `COUNTDOWN_MS / 3`; the `.na-countdown-pop` animation must fit inside one digit or it is cut off when the digit advances. `PlayGame.restart`/`restartFromCheckpoint` rewind the engine to the spawn or checkpoint *immediately*, but the frame loop only repaints the canvas when the sim advances, and during the countdown `advance` returns 0 — so the view must repaint itself. Every rewind path calls `PlayCanvas.redrawSnapped()`, which repaints once with `FollowCamera.follow(..., snap)` so the camera lands on the new pose instead of easing across the level; without it the arrow looks like it teleports only when the countdown ends. `scripts/verify-play-speed.ts` pins the 1s total, the even digit split, and that the pose is back at spawn before the countdown drains.
- **The Play tab auto-uploads finished runs and keeps a local run history.** A "Player" bar above the stage holds the name runs upload under (`naPlayName`) and an "Auto-upload runs" switch (`naPlayAutoUpload`, on by default); both persist. On a finished run `handleFinish` writes the run to a bounded local log (`src/lib/play-history.ts`, `naPlayHistory:v1`, 50 entries, shedding the oldest if the quota is tight) **before** attempting any upload, so a good run survives a restart even when the upload fails. Auto-upload is wired through `finishRef` — `loadLevel`/`onEnd` is a stable `useCallback`, so it must not close over the handler (a stale `levelName` was the bug this avoids). Only a **site** level's board auto-accepts a run: it folds to one row per player, so repeated plays just improve your row. The community TAS board keeps every entry, so it stays a manual submit (auto-posting casual plays would flood it) and a non-1× run is never auto-uploaded. The History panel (per level+arrow, like the PBs and checkpoints) shows each run's time, a PB/rate badge, and its upload outcome (`record`/`#rank`/`on board`/`failed`/`local only`); a row can be raced back as the ghost (it becomes the PB ghost), and a real-time site run whose upload failed shows a **retry** button that re-posts the logged inputs without replaying. A duplicate is treated as benign (`"already on the board"` in the 409 body), not an error toast. `scripts/verify-play-history.ts` drives the real module over a stubbed `localStorage` (ordering, per-level filter, outcome update, the cap, quota shedding, name/switch persistence, corrupt storage).
- 1v1 race ("Play" → "1v1 Race", `src/components/RaceView.tsx`) is an **asynchronous** two-player match: the host opens a lobby, shares the 6-char code, both pick the same level+arrow, and each player runs their round whenever they like. Scoring is a pure function in `src/lib/race-modes.ts` (`scoreRace(mode, players, runs)`), so all six modes (`quickfire`, `best-of-three`, `survival`, `precision`, `endurance`, `sudden-death`) share one tested code path and the UI only renders the result. `survival` drops a player's slowest run **only once both have finished all rounds**, and an incomplete player never gets a drop; "undecided" (nobody finished) is distinct from "tie" (equal times). `endurance` needs all five rounds. Lobby persistence is `src/lib/race-lobby.server.ts` (one `app_docs` doc per code, `race_lobbies` collection, service-role like the TAS board) with `isLobbyExpired`/`lobbyClosed`; a lobby seals itself (`settledAt`) the moment the match is decided and then rejects late runs ("The race window has closed."). The API is `src/routes/api/race-lobbies.index.ts` (create) and `src/routes/api/race-lobbies.$code.ts` (`join`/`submit`/`read`); `submit` re-checks membership and the pinned arrow server-side. The client (`src/lib/race-lobby.ts`) polls via `watchLobby`, and `RaceView` remembers the last lobby in `localStorage` so a reload rejoins instead of losing the match. Picking a round hands a `RacePlayTarget` up through `App` to `PlayView`, which pins the level/arrow and routes the finished run to `submitLobbyRun` instead of the public board; `App`'s `navigateView` clears that target on leaving Play so a later free-play session never silently posts to a race. `scripts/verify-race-modes.ts` (53 checks) and `scripts/verify-race-lobby.ts` (36 checks) cover the rules and the store.
- **Finished races are archived, because a lobby is not durable.** A lobby lives under its code and is dropped after `LOBBY_TTL_MS` (6h), so the match would vanish with it. `src/lib/race-matches.server.ts` writes one `app_docs` doc per match (`race_matches` collection, keyed by the lobby code, plus a `_index` doc holding the newest-first code order) the moment a lobby settles — from the `submit` path, and as a backfill on the lobby `GET` for anything settled earlier or whose archive write failed. `archivedAt` on the lobby guards both paths, so a poll writes at most once; it is stamped only after a successful write, so a failure is retried rather than lost. Archiving is **best effort** — a failed write is logged and swallowed, never failing the run the player just posted. The entry is built by the pure `buildRaceMatch`, which re-runs `scoreRace`, so an archived match can never disagree with the lobby it came from; a round a player never ran is `null`, not `0`. `archiveMatch` is idempotent per code and prunes past `RACE_MATCH_KEEP` (500) oldest-first. The "Rankings" → "Recent matches" view (`src/components/RecentMatchesView.tsx`, fed by `GET /api/race-matches` and `src/lib/race-matches.ts`) lists them newest-first with both players, the mode, the level+arrow, each player's per-round times, the date, and the winner (a trophy row plus a "Winner" badge; a drawn match says so instead). The `Σ` combined time is shown **only for `endurance`**, the one mode decided on it — on every other mode it is noise, and on `best-of-three` it would even point at the loser. `scripts/verify-race-matches.ts` (29 checks) covers the entry shape (winner, ties, per-round nulls, the survival drop, the endurance total) and the store (idempotency, newest-first, limit, the cap and pruning).
- **Player accounts are username-only, and the account is minted server-side for a reason.** `supabase.auth.signUp` cannot be used: the project requires email confirmation (`mailer_autoconfirm` off) and the address behind a username is synthetic, so the confirmation link is undeliverable and the account would be stuck permanently unconfirmed (sign-in answers `Email not confirmed`). `registerAccount` (`src/lib/accounts.functions.ts`) instead calls `supabaseAdmin.auth.admin.createUser({ email, password, email_confirm: true })` — the same service-role path the admin PIN flow uses — which yields a normal, immediately usable account with **no project setting change**. The client (`src/lib/accounts.ts`) then signs in with `signInWithPassword`, which succeeds because the account is already confirmed. Username uniqueness is the database's unique constraint on the address, so the "username is taken" check cannot be raced past; a duplicate comes back as "That username is taken."
- **The username→address mapping is shared by both sides and must never be duplicated.** `src/lib/account-email.ts` owns `USERNAME_EMAIL_DOMAIN` and `emailForAccountUsername`, imported by both the client sign-in path and the server creation function. If the two ever disagreed, sign-in would look up an address sign-up never created and every new account would be unusable. Supabase rejects reserved/placeholder domains, so a `.local` (or `example.com`) domain fails signup with "This email address is not allowed" — the domain must look real even though nothing is delivered to it. Changing it orphans every existing account; treat it as fixed. `scripts/verify-accounts.ts` (23 checks) pins the domain literally and covers normalisation, the username/password rules, and that case/space variants collapse to one address.
- **`ProfileHub` uses `useAccountAuth` + `useIsAdmin`, not `useAdminAuth`.** The sign-in section is username+password (mode toggle, no Google/email); the link request uses a `SelectionSearch` picker over the in-game names (`usernames` prop, sourced from `App`'s `allUsernames`), filtered to names not yet linked so a taken name cannot be offered. `useIsAdmin` still attempts the allow-list `claimAdmin()` on first sign-in — without it, signing in through the profile dialog would leave an admin without the role until they happened to open the admin panel. Approval also refuses to link a name already linked to a different `user_id`, since the link is the only thing that makes a profile mean anything. Accounts have no email, so a forgotten password is reset by an admin from the picker over already-linked names (`resetAccountPassword`, `src/lib/account-admin.functions.ts`).
- **A player's display name and avatar are a *presentation* layer over the in-game name, never a replacement for it.** Every board, view and API is keyed by the in-game name (`username`), and `player_profiles` is joined to it by the linked `username`; so a rename must never change an identity key or a lookup. `src/lib/display-name.ts` is the one place that resolves the pair: `displayNameFor(profiles, username)` returns the linked profile's `display_name` (whitespace-only falls back) or the in-game name, `avatarFor` the `avatar_url`, and `matchesPlayerSearch` matches **both** names — a search that only matched the in-game name would fail to find a player under the name now shown to everyone. `ProfileDirectory` is the lowercase-name→row map from `usePlayerProfiles` (`get_public_profiles()`); it is threaded into views as an optional `profiles?: ProfileDirectory` prop, so an unlinked player, a missing directory or no profile all degrade to the in-game name. Pass it through `App` — do not fetch profiles inside a view. Views carrying it: the main leaderboard table (name + avatar, gated on the `showAvatars` setting), average leaderboard, WR history, `ArrowRecordsView`, `HallOfFameView`, `MilestoneClubsView`, `PositionPointsView`, `RankPointsView`, `RecordTracker`, `PlayerVotingView`, `ImprovementTargetsView`, `RivalriesView`, `ComparePlayers`, `RecentMatchesView`, `NarrowScoreView`, `CustomCompletionsView`, `CustomsView`, `EndlessView`, `RandomLevelSelector`.
- **An avatar is downscaled in the browser and uploaded with the service role, so no storage policy is needed.** `src/lib/avatar.ts` (`fileToAvatarDataUrl`) draws the picked file to a canvas at `AVATAR_MAX_EDGE` (512) and re-encodes JPEG via an `<img>` + object URL, deliberately not `createImageBitmap` (absent on older mobile Safari, the browser this most needs to work on). `uploadAvatar` (`src/lib/avatar.functions.ts`) parses the data URL with the exported pure `decodeDataUrl` — allowlist png/jpeg/webp/gif and a 2 MB cap — and writes `${userId}/avatar.<ext>` with `upsert: true`, so re-uploading replaces the file rather than accumulating one per attempt. The `avatars` bucket is created lazily on first upload (storage schema is Supabase's, so a migration inserting into `storage.buckets` would not be applied by the normal deploy) and re-`updateBucket`ed to public if it already existed, so a hand-created private bucket cannot hand back a 403 URL. The returned URL carries `?v=<timestamp>` because the path is stable and the CDN would otherwise keep serving the previous image. **Local dev has no `SUPABASE_SERVICE_ROLE_KEY`**, so `useLocalAvatarFallback()` returns the data URL itself (same pattern as the TAS/site boards' in-memory fallback) — production always has the key and always goes to storage. `scripts/verify-avatar-upload.ts` (10 checks) pins `decodeDataUrl`; `scripts/verify-display-name.ts` (17 checks) pins the three resolvers.
- **The achievements engine (`src/lib/achievements.ts`) is surfaced on the profile as an "Achievements" tab, and its rules must never read as earned without data.** `computeAchievements(input)` is pure and derives all 10 badges from props `PlayerProfile` already has: `computedMedals` (WRs/podiums/top-10s), `Object.keys(stats.levels).length`, `levels.length`, a `PlayerScore` for the average and perfects, and the pack breakdown. The one input not already on hand is `subTenRuns`, computed by `countSubTenRuns(username, data)` over the merged boards (`levelStandings`, i.e. `processedAllLevelsData`) — it counts raw runs under `SUB_TEN_SECONDS`, not PBs, because the badge is about how many fast runs exist. **A non-positive target means "not measurable yet", so `ach()` reports `earned: false` and `progress: 0`** — a plain `value >= target` made `0 >= 0` true and unlocked every badge while the boards were still empty. `Elite Average` compares the **raw** average against 900 (rounding 899.6 up to 900 falsely unlocked it), so the display value is passed separately. The tab is `AchievementsView` (`src/components/AchievementsView.tsx`), fed `input`/`data`/`username` from `PlayerProfile`; `scripts/verify-achievements.ts` (29 checks) pins the thresholds, the empty-board guard, the 899.6 boundary and the sub-10 counter.
- **`CommandPalette` matches players by display name as well as in-game name.** cmdk filters on each item's `value`, so the player row builds it as `` `player ${displayNameFor(profiles, player)} ${player}` `` — carrying both names is what makes a renamed player findable by the name they go by, while `onSelectPlayer` still receives the in-game `username` the boards are keyed by. `App` passes `profiles={playerProfiles}`.
