- Keep navigation grouped through GroupedNavigation with secondary section views, so every feature remains accessible without overcrowding the header.
- Merge single-board and bulk-board updates into the same client leaderboard state, preserving observed PB improvements when older snapshots arrive, so profile totals stay synchronized.
- `/api/all-leaderboards` warms its persisted snapshot in `BATCH`-sized slices per request (`src/routes/api/all-leaderboards.ts`). Never fetch all `LEVELS` in one refresh: the upstream limit is ~120 req/min and a full deep load is 216 requests (~113s), which exceeds the handler's 20s wait, so nothing persists and `loaded` stays 0. Successive requests advance the warm-up and each completed slice is written to the `app_docs` snapshot.
- Profile medal data comes from the live `/user/{username}` fields `medal_counts`, `medal_counts_packs`, `medal_counts_community` (tiers: bronze/silver/gold/platinum/author), plus `custom_levels_completed`, `maps_completed`, `total_maps`, and `daily_stats`. The old `custom_medals`/`official_medals`/`pack_medals` fields never existed upstream — don't reintroduce them.
- Replay input decoding lives in `src/lib/replay.ts`: `inputs` is base64, 4 two-bit symbols per byte (MSB pair first), sampled at 240Hz (1000/240 ≈ 4.1667ms/tick). Symbols: 0=neutral/coast, 1=right steer, 2=left steer, 3=brake (both steer directions held). `ReplayViewer` collapses runs into held segments like `r72`.
- Replay physics (`src/lib/replay-sim.ts`) no longer approximates the game's `Player`. It drives the exact engine - the same Rust/WASM `GameMechanicsEngine` the Flutter app loads via `physics_core_capacitor.js` - bundled at `src/lib/physics/{rust.js,rust_bg.wasm}`. `simulateRun` is async and records one point per 240Hz input tick (`SIM_TICK_MS = 1000/240` in `replay-sim.ts`; `REPLAY_TICK_MS = 1000/240` in `replay.ts`), so the arrow's recorded rotation animates even on a spin that never translates. `SimPoint` carries the engine's own `rotation` (`rot = rotation - PI/2`) and the renderer draws the heading straight from it — never from sample displacement, which froze spins against walls. `ReplayEngine` exposes `step`/`reset`/`snapshot`/`restore` so a scrub can rewind instead of re-running from spawn. The engine's `rotation` is 0 facing -y. Symbol mapping: 1=right, 2=left, 3=brake.
- **Each arrow has its own physics.** The engine ships only a neutral default (`create_default_game_state()`), and that default is a mix of Narrow's power/startup with Speedy's energy/traction, so using it for every run makes replays DNF against walls the real run cleared. `simulateRun` now takes the run's `arrow_name` and overrides `player.constants` from `ARROW_CONSTANTS` in `replay-sim.ts` (Narrow/Speedy/Energy). Those ten values (`radius`, `engine_power`, `engine_startup_ticks`, `energy_capacity`, `energy_regeneration`, `traction_power`, `brake_power`, `aerodynamics`, `oiliness`, `turning_speed`) are the exact constants the client feeds the engine, recovered from the game's compiled Dart (`bui` in `main.dart.js`). With them, replays reproduce recorded completion times to within 1–2 ticks (verified for all three arrows on Highway Jet, and Energy on RitF).
- The bundled engine at `src/lib/physics/{rust.js,rust_bg.wasm}` supports the full `ApiObstacle` schema: `wall`, `zone` (boost/ice/nosteer/steer/rail, optional `zone_direction`), and `portal` (`portal_id` + `side`). `engineObstacles` passes every field the level uses through verbatim (`wall_type`, `wall_thickness`, `zone_type`, `zone_direction`, `portal_id`, `side`, `rotation_pivot`, `rotation_speed`, `speed`) and only infers `obstacle_type` when the payload omits it. The engine is extracted from the current Android APK (`assets/flutter_assets/assets/wasm/`) — the retired web build (`play.narrowarrow.xyz`) predates rails and portals, and the archived wasm (2026-06-13) ignores `rail` zones entirely, so don't downgrade the wasm. Rails guide the arrow along the zone's axis; without them rail levels DNF.
- Custom-level leaderboards (`CustomsView.tsx`) render the same `ReplayViewer` per row as the main leaderboard, so replays work after searching/selecting a custom level too.
- Spinning obstacles (e.g. Arrow Factory, Spinner Pack) rotate about `rotation_pivot` by `rotation_speed * tick` (radians, 240Hz tick) — verified exact against the engine's `state`. `levelWalls` carries `pivot`/`rotationSpeed` on each `SimWall`, and `ReplayViewer` applies the same transform at the current tick and bounds the camera by the swept circle. The engine already simulates the rotation, so physics never needed fixing here — only the render.
- Replay obstacle colours live in `src/lib/replay-visuals.ts` (`wallVisual(type)` → `VISUALS`, unknown types hash to a hue; `ReplayViewer`'s `ReplayLegend` reuses it). Match the game's own level renders: normal walls white, death red, bouncy green, boost blue. Keep the type keys in sync with the engine vocabulary (`wall_type`/`zone_type`).
- The TAS editor (`src/components/TasEditorView.tsx`, "Tools" → "TAS editor") loads a run's inputs or a bare level, then shows the run as a run-length list of held inputs — `Start 0.000`, one row per hold (`n 80`, `l 37`, …) with `-`/`+` to shrink/grow that hold by one 240Hz tick, then `Finish`. Growing inserts a copy of the symbol after the hold (splice) and shrinking removes the last tick; both splice/merge adjacent segments, so the displayed lengths are always exact run-lengths of `symbols`. Every edit re-simulates with the real engine from the latest checkpoint at or before the changed index (`CHECKPOINT` inputs apart), so a change near the end of a long run only re-steps the tail. It reuses the shared `ReplayStage` (exported from `ReplayViewer`) with `hideControls`. The "Leaderboard" popover lists the selected level's board so a run can be picked by name (auto-switches level/arrow). "Go to time (s)" jumps the frame; note `path[0]` is the spawn pose so input `i` lands on `path[i + 1]`.
- The leaderboard cache (`src/services/api.ts`) merges via `mergeLeaderboardUpdates` (`src/lib/leaderboard-state.ts`) on both the bulk and single-board paths, so a single-board refresh never drops a PB the bulk snapshot already surfaced. The `all-leaderboards` route warms the persisted `app_docs` snapshot in `BATCH`-sized slices per request; never fetch all `LEVELS` in one refresh (upstream limit ~120 req/min; a full deep load exceeds the handler's 20s wait).
- The upstream API (`api.narrowarrow.xyz`) is read-only in this repo: every route is a `GET` through `na-proxy.ts`, and the run payload (`/runs/<id>`) is `{ runId, mapName, arrow_name, inputs, input_count, verified, completion_time, finishedAt, skinConfig, isCustomLevel }` — it carries no user id and no submit/upload endpoint. So a TAS run can't be pushed into the game's own leaderboard (nor onto a copied level) from here; the TAS board below is the sanctioned place to post one. Re-submitting to the real game would need a game account and the game's own client flow, which this site doesn't implement.
- The community TAS leaderboard is site-owned, not the real game board — it exists precisely so tool-assisted runs can be shared without touching the official leaderboard. Storage is `src/lib/tas-board.server.ts` (one `app_docs` doc per level, collection `tas_boards`, entries sorted by time then creation). The API is `src/routes/api/tas-leaderboard.$level.ts`: `GET` returns the level's sorted entries (anon-readable), `POST` validates the name/time/input string, appends, and returns `{ isRecord, rank, entries }`; `DELETE ?id=` removes one entry and is admin-only (`verifyAdminRequest` re-checks `user_roles` server-side, so hiding the button in the UI is not the gate). Client helpers live in `src/lib/tas-leaderboard.ts`. The editor's "Submit TAS" button opens `TasSubmitDialog` (name + fixed time; the input string is attached automatically from the current `symbols`), and the editor shows the level's TAS board with a "New TAS record!" toast when the submitted time beats the existing best. `app_docs` writes need the service role, which local dev lacks — `tas-board.server.ts` falls back to a per-process in-memory board when `SUPABASE_SERVICE_ROLE_KEY` is unset and `NODE_ENV !== "production"`; production always uses Supabase.
- The TAS board (`TasLeaderboardView`, "Tools" → "TAS leaderboard") lists the selected level's entries with the fastest pinned as `WR`. Every row can be watched in-place via `TasReplayViewer` (`ReplayViewer.tsx`), which plays straight from the stored input string with the real engine — no upstream run id needed — and loaded into the editor via the pencil button, which hands a `TasLoadRequest` (`{levelId, arrowName, inputs, inputCount}`) up through `App` to `TasEditorView`. Submissions must be distinct runs: `POST` rejects an input string already on the board with `409`, so a loaded WR can't be re-submitted untouched (edit it first). Its wide table (7 columns) must stay inside an `overflow-x-auto` wrapper — without it the rightmost Actions column (watch/load/delete) is clipped off-screen and unreachable on narrow viewports, since the enclosing card is `overflow-hidden`.
- The main leaderboard shows the level's community TAS time instead of the old theoretical/human limit cards. It is fetched per selected level via `fetchBestTasTime` and renders `N/A` when the level has no TAS submissions.
