- Replay input decoding lives in `src/lib/replay.ts`: `inputs` is base64, 4 two-bit symbols per byte (MSB pair first), sampled at 240Hz (1000/240 Ōēł 4.1667ms/tick). Symbols: 0=neutral/coast, 1=right steer, 2=left steer, 3=brake (both steer directions held). `ReplayViewer` collapses runs into held segments like `r72`.
- Replay physics (`src/lib/replay-sim.ts`) no longer approximates the game's `Player`. It drives the exact engine - the same Rust/WASM `GameMechanicsEngine` the Flutter app loads via `physics_core_capacitor.js` - bundled at `src/lib/physics/{rust.js,rust_bg.wasm}`. `simulateRun` is async and records one point per 240Hz input tick (`SIM_TICK_MS = 1000/240` in `replay-sim.ts`; `REPLAY_TICK_MS = 1000/240` in `replay.ts`), so the arrow's recorded rotation animates even on a spin that never translates. `SimPoint` carries the engine's own `rotation` (`rot = rotation - PI/2`) and the renderer draws the heading straight from it ŌĆö never from sample displacement, which froze spins against walls. `ReplayEngine` exposes `step`/`reset`/`snapshot`/`restore` so a scrub can rewind instead of re-running from spawn. The engine's `rotation` is 0 facing -y. Symbol mapping: 1=right, 2=left, 3=brake.
- **Each arrow has its own physics.** The engine ships only a neutral default (`create_default_game_state()`), and that default is a mix of Narrow's power/startup with Speedy's energy/traction, so using it for every run makes replays DNF against walls the real run cleared. `simulateRun` now takes the run's `arrow_name` and overrides `player.constants` from `ARROW_CONSTANTS` in `replay-sim.ts` (Narrow/Speedy/Energy). Those ten values (`radius`, `engine_power`, `engine_startup_ticks`, `energy_capacity`, `energy_regeneration`, `traction_power`, `brake_power`, `aerodynamics`, `oiliness`, `turning_speed`) are the exact constants the client feeds the engine, recovered from the game's compiled Dart (`bui` in `main.dart.js`). With them, replays reproduce recorded completion times to within 1ŌĆō2 ticks (verified for all three arrows on Highway Jet, and Energy on RitF).
- The bundled engine at `src/lib/physics/{rust.js,rust_bg.wasm}` supports the full `ApiObstacle` schema: `wall`, `zone` (boost/ice/nosteer/steer/rail, optional `zone_direction`), and `portal` (`portal_id` + `side`). `engineObstacles` passes every field the level uses through verbatim (`wall_type`, `wall_thickness`, `zone_type`, `zone_direction`, `portal_id`, `side`, `rotation_pivot`, `rotation_speed`, `speed`) and only infers `obstacle_type` when the payload omits it. - The TAS "Brute optimizer" (`BruteView.tsx`, Tools group) is admin-gated: it seeds a search from the selected level's fastest TAS run and hill-climbs the input string with the real engine (`optimizeRun` in `src/lib/tas-brute.ts`), then offers "Submit as my TAS" through the same `TasSubmitDialog`. - When optimizing a replay offline, always feed the engine the run real `arrow_name` constants (`ARROW_CONSTANTS` in `replay-sim.ts`) - with the default constants a valid run DNFs, and any time measured against it is meaningless. Reusing the engine `GameMechanicsEngine.from_state` snapshot at a checkpoint is ~2x faster than re-running the prefix, so an incremental search over the tail is the practical way to squeeze a run.
- Input semantics (from instrumenting the engine on open ground): symbol 0 (neutral) coasts along the current heading and thrusts straight ahead, accelerating to a terminal ~2.39 for Narrow; a held turn (1 right / 2 left) rotates the heading ~0.013 rad/tick, so the thrust points away from the velocity and bleeds speed (circling settles at ~0.52). So a straighter line is faster and the level's walls do the turning for you; a real maze run reaches ~1.6 because corners force turning. Symbol 3 (brake) scrubs speed hard. The trajectory is slidey (`oiliness` 0.996), so the arrow drifts and the heading often sits well off the velocity.
- The offline hill-climb plateaus after a few ticks, so the productive search is simulated annealing plus a "straighten" mutation that replaces held turns in a random window with neutral (exploiting the speed-vs-turn trade-off above). For Moon Rock Rally (`0CFAEE35`) this took the Narrow line 11.829s (real WR) -> 11.7458s in ~1h on 4 cores; ~1 tick per 10 min once near the plateau.

- The brute harness's DNF fitness gradient can be a trap when the level's `finish` wall sits **behind a death wall** (Turnpike Drift: finish #33 and death #26 are parallel, so the finish *midpoint* is unreachable and the gradient parks a run against the death wall). - `BAN_BRAKE=lo,hi` forbids the brake symbol in a tick range, so the search must make that turn some other way. Useful for testing "can this corner be taken without braking" ŌĆö but on a tight weave the brake is often load-bearing: the arrow (~22 units wide) threads a channel barely wider than itself, so removing the brake DNFs. A run that clears the weave brakeless is not automatically faster either; on Turnpike Drift a brakeless line reached the finish *area* ~5s early yet could not enter, because the finish is only reachable from the opposite side of the death wall.

- The brute optimizer (`tas-brute.ts`) scores every candidate through `CheckpointSim`, which skips the shared prefix instead of re-running from spawn: it snapshots a reference stream every 60 ticks (`stride`), finds the deepest checkpoint whose whole prefix matches the candidate, restores it and steps only the tail. Candidates that edit early miss and fall back to a full replay. The search re-anchors the checkpoints via the `onRef` hook (called on every accepted anneal move and every refine improvement); `setRef` rebuilds only the tail past the divergence, so following `cur` is cheap. Measured on MRR: ~1.6x more evals in an isolated loop, ~1.2x end-to-end, scores bit-identical (the engine `snapshot()`/`restore()` round-trips exactly; verified over 800 candidates). `mutate` also has a `wider entry, tighter exit` move (m===12) that lengthens one side of a turn boundary and shortens the other.

- The brute progress panel (`BruteView.tsx`) keeps a per-worker ledger and `publishProgress()` sums Generations/Rollouts across all workers (best tick = min across workers).
